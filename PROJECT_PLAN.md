# GraphRAG-V1 Project Plan

## Project Background

This project is a Chinese criminal-law case question-answering system. The target architecture is not a rule answer engine. The final answer should be generated by an LLM from controlled, explainable, traceable retrieval context.

The system must support:

- case, law article, reasoning, defense, evidence, and judgment retrieval;
- graph-based multi-hop retrieval over case and law structure;
- vector retrieval over normalized chunks;
- hybrid top-k context selection for LLM answering;
- citations, graph paths, warnings, and refusal behavior;
- low-confidence protection before passing context to the LLM.

Current work is still a small-sample data and retrieval foundation. Do not build full-scale indexes, graph databases, Neo4j, or full-data production pipelines until the sample pipeline and schema are stable.

## Current Implementation

The current sample pipeline builds normalized data under `processing_data/`:

- `law_articles_sample.jsonl`
- `cases_sample.jsonl`
- `cases_enriched_sample.jsonl`
- `case_chunks_sample.jsonl`
- `law_chunks_sample.jsonl`
- `retrieval_chunks_sample.jsonl`
- `graph_sample.jsonl`
- sample quality and eval reports

The current answer layer is rule-based:

- `processing/search_sample.py` performs lexical retrieval and graph expansion.
- `processing/answer_sample.py` generates rule answers from search results.
- answer output includes `answer`, `citations`, `graph_paths`, `warnings`, and search summary.
- `processing/answer_eval_sample.py` checks small-sample behavior for sentence, applied articles, facts, evidence, reasoning, defense, amounts, refusal, and out-of-scope queries.

This is useful as a sample validation harness, but it is not the final full-system answer strategy.

The current API answer layer also has a guarded LLM path:

- `app/llm/chat_service.py` calls hybrid retrieval, applies confidence gating, builds strict JSON prompts, validates LLM citation IDs, and falls back to retrieval summaries when LLM output is invalid.
- `POST /api/chat` keeps the stable chat contract for the frontend.
- `POST /api/chat/orchestration` exposes an experimental LangChain-core orchestration wrapper with mock LLM modes and `orchestration_logs`; it does not replace `/api/chat`.
- `/api/chat/orchestration` supports `generation_mode=mock` by default and `generation_mode=provider` for explicit DeepSeek/OpenAI-compatible provider orchestration when credentials are configured.
- `processing/langchain_orchestration_eval_sample.py` verifies the wrapper with deterministic mock LLM outputs before any provider-backed orchestration path is trusted.
- The frontend keeps stable chat as the default path and exposes an explicit experiment switch for `/api/chat/orchestration`, with logs shown only when orchestration responses include them.

## Current Bias And Gap

The ideal system should use the graph as a retrieval tool. For example, a query may start from a case, move through applied law articles, then retrieve related clauses, reasoning chunks, defense chunks, and judgment chunks.

The current system does not do that yet:

- lexical hits still drive initial recall;
- graph expansion mainly supplies traceable paths and answer verification;
- graph structure is not yet used as a first-class chunk recall mechanism;
- rule answers encode small-sample behavior that will not generalize to full data;
- lexical weight tuning, short-name handling, and refusal rules are sample-specific and should not be treated as final production logic.

Therefore, the next major direction is vectorized retrieval plus graph recall, then hybrid context assembly for an LLM.

## Target Architecture

The self-owned processing and retrieval pipeline remains the source of truth. It owns data extraction, normalization, graph snapshots, lexical/vector/graph/hybrid retrieval, ranking diagnostics, quality reports, confidence gating, refusal behavior, and citation evidence.

LangChain may be introduced only as an orchestration-layer experiment. It should call the existing pipeline modules as tools or runnables, manage multi-turn conversation flow, and collect callback/log output, but it must not replace the deterministic retrieval, graph path tracing, confidence gate, refusal, or citation contract.

### 1. Graph Recall

Graph recall reads `graph_sample.jsonl` and chunk metadata to retrieve related chunks through structured paths.

Responsibilities:

- map query intent to graph traversal targets;
- support case-to-article, case-to-reasoning, case-to-defense, and article-to-case paths;
- preserve graph path evidence in output;
- avoid mapping historical law articles to current law chunks unless `law_version=current`;
- return candidate chunk IDs and graph path metadata, not final natural-language answers.

Example paths:

- `case -> CASE_APPLIES_ARTICLE -> current law article chunk`
- `case -> reasoning_text chunk -> applied article`
- `case -> defense_text chunk -> reasoning_text chunk`
- `article -> cases that apply article -> judgment/reasoning chunks`

### 2. Vector Search

Vector search embeds chunks from `retrieval_chunks_sample.jsonl` and embeds the query at search time.

Responsibilities:

- use a local embedding model, default `BAAI/bge-base-zh-v1.5`;
- store a local FAISS index under `processing_data/vector_index_sample/`;
- keep metadata aligned with existing chunk schema;
- return top-k chunks with similarity scores;
- support rebuild from JSONL without mutating `raw/`.

Required metadata:

- `retrieval_id`
- `source_type`
- `case_id`
- `title`
- `field`
- `article_no`
- `law_name`
- `law_version`
- `source_file`
- `text_hash`

### 3. Hybrid Search

Hybrid search merges graph recall and vector search candidates.

Responsibilities:

- deduplicate by `retrieval_id`;
- rank by vector score, graph path strength, source type, field, and law version;
- prefer chunks that are both vector-relevant and graph-connected;
- keep historical law chunks separate from current law chunks;
- return a compact top-k context package for the LLM.

The hybrid output should include:

- selected chunks;
- retrieval scores;
- source metadata;
- graph paths;
- warnings;
- rejected or low-confidence reasons when applicable.

### 4. LLM Answer Generation

The LLM answer step should consume only the hybrid top-k context, not raw files.

Responsibilities:

- generate concise Chinese answers grounded in retrieved context;
- cite chunk IDs, case titles, article numbers, and graph paths;
- refuse unsupported, out-of-scope, or low-confidence questions;
- expose warnings such as `no_current_law_chunk`, `low_similarity`, `case_not_found`, and `insufficient_context`;
- never invent law text or case facts not present in context.

## LangChain Integration Boundary

Use LangChain for:

- orchestration-layer experiments over the existing retrieval and answer pipeline;
- calling self-owned pipeline functions such as hybrid search, confidence evaluation, prompt assembly, and LLM/mock LLM answer steps;
- multi-turn conversation state management without treating old assistant answers as hidden evidence;
- callback and log collection for intermediate pipeline outputs, including query profile, selected context, ranking adjustments, graph paths, warnings, citations, confidence, refusal reason, and LLM/mock LLM raw output;
- mock LLM runs that allow answer eval to execute without an external provider;
- optional document/runnable wrappers when they preserve the existing metadata contract exactly.

Do not use LangChain for:

- parsing raw case files;
- mutating `raw/`;
- replacing the JSONL processing pipeline;
- replacing self-owned lexical, vector, graph, or hybrid retrieval scoring;
- hiding graph path provenance, ranking diagnostics, citation IDs, source files, text hashes, confidence inputs, warnings, or refusal reasons;
- hiding metadata validation;
- hard-coding sample answer behavior;
- agent-style autonomous tool use in the answer path;
- letting the LLM read `raw/` or any source outside the retrieved context.

Required LangChain experiment guarantees:

- hybrid retrieval remains tunable and explainable outside LangChain;
- graph paths remain traceable from final answer citations back to graph edges and chunks;
- confidence gate, refusal behavior, and citation validity remain independently testable;
- LangChain callbacks/logs expose self-owned pipeline intermediate outputs;
- the wrapped chain can run deterministic simulated eval with mock LLM JSON output before any provider-backed LLM run is trusted.

## Rule Handling

### Keep For Now

- deterministic data parsing rules;
- law article extraction rules;
- `law_version` detection;
- current law versus 1979 law separation;
- metadata validation;
- sample answer eval expectations;
- refusal warnings in rule answer output while `answer_sample.py` remains active.

### Rework

- lexical field weights should become a weak baseline signal, not the main retrieval strategy;
- short case-name handling should move into a query interpretation or candidate validation step;
- requested article checks should become metadata filters in graph/vector/hybrid retrieval;
- refusal behavior should move toward a confidence gate using retrieval evidence, not answer-specific rule branches.

### Deprecate For Full System

- rule-written final answers;
- eval-specific refusal patches;
- hard-coded answer routing as the production answer engine;
- direct dependence on lexical hits for graph expansion.

## Safety And Confidence Controls

Safety controls should happen before LLM answer generation.

Required controls:

- metadata validation for every selected chunk;
- similarity threshold for vector hits;
- graph path validation for graph-expanded chunks;
- law version guard: only attach current law chunk when `law_version=current`;
- minimum context threshold before allowing LLM generation;
- refusal path with empty citations when context is insufficient;
- warnings for partial retrieval, missing current law chunk, low similarity, and unsupported query type.

Later confidence gate inputs:

- top vector score;
- score gap between top hits;
- number of graph-connected chunks;
- required metadata match;
- case title match strength;
- requested article match;
- out-of-scope classifier or rules.

## Evaluation Plan

Run the existing validation commands after each change:

```powershell
python processing\run_sample_pipeline.py
python processing\search_eval_sample.py --fail-on-warn
python processing\answer_eval_sample.py --fail-on-warn
python processing\vector_search_eval_sample.py --fail-on-warn
python processing\hybrid_search_eval_sample.py --fail-on-warn
python -m pytest tests\test_api_chat.py
cd frontend; npm test
cd frontend; npm run build
```

Do not run the sample pipeline in parallel with eval commands that read `processing_data/` JSONL files. Run the commands sequentially so eval does not read files while the pipeline is rewriting them.

Use the existing vector index build command only when the retrieval chunks or embedding config changed:

```powershell
python processing\embed_retrieval_chunks_sample.py
```

Add orchestration eval before trusting LangChain-wrapped answer behavior:

```powershell
python processing\langchain_orchestration_eval_sample.py --fail-on-warn
```

This eval should use mock LLM JSON output first. It must assert that LangChain callbacks/logs include the self-owned pipeline's intermediate outputs and that final `citations`, `graph_paths`, `warnings`, `confidence`, and `refusal_reason` remain valid.

Key eval cases:

- Wu Biding sentence query;
- Wu Biding applied articles;
- Wu Biding current law only;
- Wu Biding 1979 law warning;
- law article lookup by article number;
- fact, evidence, reasoning, and defense retrieval;
- nonexistent case refusal;
- nonexistent article refusal;
- out-of-scope refusal;
- cross-case comparison unsupported warning;
- LangChain wrapped orchestration produces the same retrieval context as direct hybrid search;
- mock LLM invalid JSON, missing citation IDs, empty answers, low confidence, and out-of-scope queries trigger the same fallback/refusal behavior as the direct service path.

## Action Items

1. Preserve the self-owned retrieval baseline.
   - Keep `processing/run_sample_pipeline.py`, lexical search, graph retriever, vector search, and hybrid search as direct Python modules.
   - Keep hybrid constants, intent boosts, diversity penalties, and diagnostics editable outside LangChain.
   - Run the validation commands sequentially after retrieval changes.

2. Keep graph path and citation provenance explicit.
   - Preserve `graph_paths`, `retrieval_id`, `chunk_id`, `source_file`, `text_hash`, `article_no`, `law_version`, and evidence previews in selected context and final citations.
   - Verify final citations refer only to IDs present in `retrieval_context`.

3. Keep confidence, refusal, and fallback behavior independently testable.
   - Keep the confidence gate outside LangChain-specific abstractions.
   - Preserve refusal reasons for `insufficient_context`, `low_confidence`, `out_of_scope`, invalid LLM JSON, empty answer, and missing valid citation IDs.

4. Add LangChain only at the orchestration layer.
   - Add `processing/langchain_orchestration_sample.py` or an equivalent app-layer module that wraps existing pipeline calls.
   - Use LangChain to manage call order and multi-turn state, not to replace retrieval scoring or metadata validation.
   - Do not pass prior assistant answers to the LLM as hidden evidence.

5. Add callback/log capture around wrapped pipeline calls.
   - Capture query profile, lexical/vector/graph hit summaries, selected context, ranking adjustments, graph paths, warnings, confidence, citations, refusal reason, and raw LLM/mock LLM output.
   - Store logs in memory or eval output first; do not create a production trace store yet.

6. Add mock LLM orchestration eval.
   - Add `processing_data/langchain_orchestration_eval_sample.json`.
   - Add `processing/langchain_orchestration_eval_sample.py`.
   - Use deterministic mock LLM JSON to test valid answers, refusal, invalid JSON fallback, missing citation ID fallback, and low-confidence behavior.

7. Compare wrapped versus direct behavior.
   - Assert LangChain-wrapped hybrid retrieval returns the same selected context, graph paths, warnings, and confidence as the direct `hybrid_search_sample.py` plus existing chat service path for the same query.
   - Treat any unexplained difference as a regression unless explicitly approved.

8. Keep provider-backed LLM optional.
   - Use the configured DeepSeek/OpenAI-compatible provider only when `generation_mode=provider` is explicitly requested and credentials are configured.
   - Keep the direct provider client behavior and fallback path available while the LangChain wrapper is experimental.

9. Promote orchestration only after endpoint-level evidence is stable.
   - Keep `/api/chat/orchestration` separate from `/api/chat`; the frontend may expose both paths but must default to stable chat.
   - If provider-backed orchestration is added, gate it with config and retain deterministic mock mode for regression tests.

## First Implementation Milestone

The current concrete milestone is:

1. keep the current sample pipeline, retrieval evals, API tests, and frontend checks green;
2. add a LangChain orchestration wrapper that calls the existing hybrid retrieval and answer contract without changing retrieval output;
3. add callback/log capture for self-owned pipeline intermediate outputs;
